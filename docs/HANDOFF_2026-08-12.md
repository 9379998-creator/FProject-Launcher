# Handoff 2026-08-12

## С чего начали

Launcher v3 уже имел рабочую левую панель с объектами, деревом и PDF-просмотрщиком, но оставались две большие проблемы:

1. Массовый рендер PDF в 300 DPI был слишком долгим.
2. В дереве объекта не хватало ширины для длинных имён файлов и папок.

Отдельно была постоянная тревога по поводу Google Drive `H:`: казалось, что время уходит на скачивание/синхронизацию файлов перед рендером.

## Что замерили

Был выполнен тест одного и того же PDF с `H:` и локальной копии на `C:`.

Результат:

- чтение с `H:` занимало доли секунды;
- копирование с `H:` на `C:` занимало доли секунды;
- рендер одной страницы Poppler занимал секунды;
- рендер с `H:` и с `C:` отличался минимально.

Вывод: в текущем тесте основное время тратится не на Google Drive, а на сам рендер PDF в PNG. Если файл ещё не синхронизирован Google Drive Desktop, первый доступ может быть медленнее, но для уже доступных файлов узкое место - Poppler/render.

## Главное принятое решение дня

Не рендерить всю пачку PDF сразу в максимальном качестве.

Новая схема:

1. Для массового обзора рендерить PDF в лёгком качестве.
2. Для реально открытой страницы дорендеривать качество 300 DPI.
3. Складывать оба результата в кэш.
4. Не заставлять пользователя ждать полный 300 DPI для 100+ PDF, если он реально откроет только часть листов.

## Что реализовано

### 1. Быстрый PDF-обзор

Массовый рендер выбранной пачки PDF теперь идёт в `150 DPI`.

Это используется для:

- ленты миниатюр;
- первичного просмотра;
- быстрого понимания состава пачки.

На пользовательском тесте папка с примерно 150-160 листами отрендерилась примерно за 5 минут. Это принято как терпимый уровень для текущей стадии.

### 2. Качество по выбранной странице

Добавлен backend endpoint:

```text
POST /api/pdf/page
```

Он рендерит одну конкретную страницу конкретного PDF в указанном DPI.

Frontend использует это так:

- сначала показывает страницу из быстрого обзора `150 DPI`;
- затем автоматически запрашивает эту же страницу в `300 DPI`;
- после готовности подменяет картинку в большом viewer;
- повторное открытие использует кэш.

### 3. Индикатор качества активного листа

В viewer добавлен небольшой индикатор:

- `Обзор 150 DPI`;
- `Качество 300 DPI загружается…`;
- `Качество 300 DPI`;
- если качество не получилось получить, показывается состояние `качество недоступно`.

Цель: больше не гадать, что сейчас на экране - preview или финальное качество.

### 4. Широкий режим дерева

Когда объект открыт для выбора файлов, дерево теперь занимает правую область экрана.

Логика:

- режим выбора файлов: справа широкое дерево с полными именами;
- после нажатия `Отобразить`: справа снова PDF-viewer с миниатюрами и большим листом;
- левая панель остаётся управляющей зоной.

Это решает проблему длинных имён файлов без увеличения постоянной ширины левой панели.

На конец дня принято:

# Дополнение 2026-08-12 — DWG этап принят

## С чего начали DWG-блок

После принятого PDF-viewer нужно было распространить принцип Launcher на DWG.

Пользовательская логика:

- DWG не нужно превращать в полноценный встроенный CAD-viewer;
- DWG обычно имеет PDF-пару;
- PDF-пара должна служить визуальным preview для DWG;
- сам DWG должен открываться в установленной нативной программе Windows.

## Что реализовано

### 1. Открытие исходного файла

В backend добавлен endpoint:

```text
POST /api/open-file
```

Он открывает файл через системную ассоциацию Windows.

Для DWG это значит:

- если установлен AutoCAD, DWG TrueView или другой viewer, Windows откроет DWG через него;
- Launcher не выбирает CAD-программу сам;
- выбор приложения остаётся ответственностью Windows и пользователя.

### 2. DWG/PDF pairing

В frontend добавлено сопоставление DWG с PDF.

Поведение:

- DWG с найденной PDF-парой отображается через PDF-preview;
- DWG без пары не исчезает;
- для DWG без пары показывается карточка `Нет PDF-пары`;
- в обоих случаях остаётся возможность открыть исходный DWG.

### 3. Усиленный алгоритм имён

Алгоритм сопоставления был переделан после проверки реального блока `АР2.2.2`.

Теперь он учитывает:

- `АР2-2-2` и `АР2.2.2` как один шифр;
- разные разделители и служебные префиксы;
- длинные совпадающие фразы;
- последовательности совпадающих слов;
- смысловые токены основного названия листа;
- жёсткое различение `Часть 1` и `Часть 2`;
- запрет связи между разными разделами, например `АР3.2` не должен цепляться к `АР2.2.2`.

Проверенные примеры:

- `Ведомости отделки помещений — Часть 1.dwg` нашёл `... Часть 1.pdf`;
- `Ведомости отделки помещений — Часть 2.dwg` нашёл `... Часть 2.pdf`;
- `Маркировочный план 16-18 этажей...dwg` нашёл PDF даже при отличии номера листа;
- `Маркировочный план технического пространства...dwg` нашёл PDF даже при отличии номера листа;
- чужой шифр не связался.

## Что принято пользователем

Пользователь принял:

- сопоставление DWG/PDF;
- скорость открытия DWG;
- текущий уровень ошибок как допустимый для checkpoint;
- возможность потом точечно доработать редкие пары.

# Дополнение 2026-08-12 — Вортекс Word принят

## Что сделано

Начат модуль `Вортекс` — универсальный preview-поток для разных форматов.

Первым форматом выбран Word.

Реализовано:

- `.doc` и `.docx` конвертируются через Microsoft Word в PDF-кэш;
- полученный PDF идёт в уже принятый PDF render pipeline;
- viewer, миниатюры, масштаб, лапа, поворот и режимы просмотра используются без отдельного Word-viewer;
- кнопка native open называется `Открыть Word`;
- `.gdoc` добавлен как Google Docs shortcut: visible/selectable/openable, но без локального Word-preview;
- кнопка для `.gdoc` называется `Открыть Google Docs`.

## Принятый принцип

Word внутри Launcher не редактируется.

Launcher:

- показывает preview;
- помогает быстро понять содержимое;
- открывает исходный файл в Word/Google Docs при необходимости.

## Проверка

Backend smoke test:

- файл: `ссылка на тендер.docx`;
- первый прогон: 1 страница, ошибок 0;
- повторный прогон: около 0.5 сек;
- `convertCacheHit=True`;
- `cacheHit=True`.

Пользователь подтвердил: Word/GDOC работает, можно фиксировать checkpoint.
