# Запрос независимой оценки: следующий шаг Excel-preview в F-Engineering Launcher

## Зачем этот документ

Нужна независимая оценка архитектурного решения для просмотра Excel-книг в
F-Engineering Launcher. Просьба не предлагать код до ответа по существу:
правильно ли выбран следующий шаг и какие риски в нём не учтены.

## Контекст продукта

Launcher — локальный навигатор по большим структурам проектных файлов. Его
смысл не в редактировании документов и не в создании второго Excel. Пользователь
должен быстро понять, **какие из десятков файлов ему нужны**, оставаясь в одной
среде:

1. выбрать группу файлов;
2. увидеть их визуальные миниатюры;
3. выбрать интересующую миниатюру и увидеть её крупнее;
4. только если нужно работать с данными — открыть исходник в нативной программе.

Этот принцип уже принят и работает для PDF, DWG (через связанные PDF) и Word.

## Что сейчас сделано для Excel

В текущей незавершённой ветке есть:

- сервер на Python;
- чтение `.xlsx` / `.xlsm` через `openpyxl`;
- прототип подробного HTML-представления отдельного листа;
- вкладки листов, прокрутка, масштаб и режим руки;
- попытка показывать несколько выбранных книг в левой ленте;
- старый резервный путь `Excel → PDF → PNG`.

Нативное открытие файла в установленной программе уже существует как отдельное
действие.

## Что фактически не работает и почему это важно

Текущий Excel-модуль не принят пользователем.

- Для выбранной книги на экране возникал белый лист вместо содержимого.
- Одна причина уже найдена: книга с листом без сохранённого размера области
  вызывала исключение при создании миниатюры; при этом UI ошибочно показывал 100%.
- После устранения этой ошибки сервер начал возвращать метаданные и вкладки, но
  подробный HTML первого листа оказался тяжёлым: около 4–9 МБ для 2 000 строк.
- Главная проблема не только техническая: лента полезных визуальных миниатюр
  книг всё равно не появилась. Следовательно, продуктовая цель не достигнута.

Пользователь справедливо отметил: без миниатюр Launcher не даёт преимущества
перед обычным открытием файлов в Excel.

## Моя предлагаемая позиция

Остановить дальнейшие интеграционные исправления текущего Excel HTML-viewer и
сначала создать отдельный, изолированный прототип **быстрого визуального
предпросмотра**.

```text
XLS/XLSX
  → быстрый разбор структуры
  → выбор активного либо первого содержательного листа
  → preview.webp / preview.png
  → кэш
  → мгновенная лента миниатюр
  → клик: крупная готовая картинка
  → по запросу: подробный HTML-просмотр листа
  → по запросу: «Открыть в Excel»
```

### Разделение уровней

| Уровень | Назначение | Когда создаётся |
|---|---|---|
| Fast preview | Миниатюра/крупная картинка, чтобы понять тип и содержание книги | Один раз, фоном; далее из кэша |
| Sheet preview | Карточки отдельных листов выбранной книги | Лениво, после интереса к книге |
| Deep view | HTML-лист с прокруткой, масштабом, рукой и вкладками | Только по явному запросу |
| Native open | Редактирование и полноценная работа | Только по кнопке |

Для многостраничных книг дополнительно предлагается оценить «контактную
карточку»: первый содержательный лист крупно плюс 2–3 уменьшенных фрагмента
следующих содержательных листов. Так на миниатюре быстрее видно различие между
сметой, реестром, расчётом, графиком и пустой книгой.

## Что намеренно не предлагается сейчас

- Не внедрять Univer / аналог полноценного браузерного Excel-редактора.
- Не строить HTML всех книг и всех листов при выборе пачки файлов.
- Не считать PDF обязательным основным промежуточным форматом.
- Не использовать Excel Preview Handler как основной встроенный viewer.

На компьютере зарегистрированы `Microsoft Excel previewer` и `WPS Spreadsheets
Preview Handler`. Их стоит испытать как ориентир качества и отдельный резервный
вариант. Но Preview Handler — нативный Windows COM-компонент, которому требуется
desktop-host; он не встраивается напрямую в браузерный интерфейс Launcher и не
решает сам по себе задачу кэшированных миниатюр.

## Предлагаемый порядок работ

1. **Анализ без изменения основного Launcher.** Выбрать parser и renderer для
   `.xlsx`, `.xlsm`, `.xls`; определить ограничения первой версии.
2. **Отдельный прототип на одном реальном файле.**
   `input.xlsx → preview.webp`; измерить время, размер и визуальную полезность.
3. **Сравнительный тест.** Не менее 10–20 реальных книг, включая длинные,
   широкие, многостраничные и старые `.xls`.
4. **Только после приёмки пользователем** встроить кэшированную ленту карточек
   в Launcher.
5. Затем — подробный viewer листов и проверка на реальной Chrome-вкладке
   пользователя.

## Предварительные критерии приёмки

- Нет белого экрана и ложного сообщения «100%» при ошибке.
- По карточке можно определить, что перед нами: смета, реестр, расчёт, график,
  спецификация, пустая/неинтересная книга.
- Повторный показ из кэша не запускает Excel и происходит практически сразу.
- Переключение на соседнюю карточку не строит тяжёлый HTML.
- Подробный просмотр загружается только после выбора конкретной книги/листа.
- Если preview нельзя сформировать, показывается понятное состояние и доступна
  кнопка открытия в нативной программе — не пустое поле.

## Вопросы эксперту

1. Согласны ли вы, что Fast preview должен стать первым и обязательным уровнем,
   а HTML deep view — вторым, ленивым уровнем?
2. Какие варианты parser + renderer вы рекомендуете для локальной работы с
   `.xlsx`, `.xlsm` и `.xls`, если важны скорость, исходное оформление, merged
   cells, размеры строк/столбцов, изображения, диаграммы и сохранённые результаты
   формул?
3. Имеет ли смысл в качестве первого прототипа рендерить напрямую в PNG/WebP:
   через HTML + headless browser, Canvas или другой локальный renderer?
4. В каких случаях допустимо использовать `Excel → PDF → PNG/WebP` как fallback,
   не превращая его в основной путь?
5. Что практичнее для карточки многостраничной книги: только активный лист,
   первый содержательный лист или контактная карточка из нескольких листов?
6. Какие ключи кэша обязательны, чтобы превью не устаревало, но не
   перегенерировалось без причины?
7. Нужен ли Univer после появления Fast preview и лёгкого HTML deep view? Если
   да, какие конкретные задачи он окупит?
8. Реалистичны ли ориентиры: первый preview — в фоне, cached preview — почти
   мгновенно, навигация по соседним готовым карточкам — без парсинга Excel?
9. Какие ограничения первой версии вы считаете правильными и честными?
10. Поддерживаете ли вы решение **не менять основной Launcher до приёмки
    отдельного прототипа**?
