# F-Engineering Launcher v3 — подробная передача проекта

Дата: 15.08.2026  
Статус: рабочий Launcher v3 существует локально; базовые контуры PDF, DWG, Word и Excel приняты пользователем. Дальнейшая работа должна идти только малыми проверяемыми изменениями.

## 1. Цель продукта

Launcher — не замена Windows Explorer, AutoCAD, Word или Excel и не «чат с ИИ». Его назначение — быстро дать человеку визуальное представление о большой структуре проектных документов:

1. подключить папку объекта;
2. увидеть дерево, длинные имена и фильтры форматов;
3. выбрать сразу несколько интересующих файлов;
4. быстро просмотреть их визуально через кэшированные превью и большой viewer;
5. открыть только действительно нужный исходный файл в его нативной программе;
6. позднее запускать ограниченные, прозрачные модули обработки с известными входами, выходами и журналом.

Ключевая ценность — не «открыть файл вместо программы», а убрать медленное перебирание сотен файлов по именам. Пользователь должен сначала видеть содержание глазами (карточки/миниатюры → большой просмотр), затем решить, нужно ли открывать исходник.

## 4. Что работает и принято

### Объекты и дерево

- Добавление, обновление, исключение объектов.
- Просмотр нескольких объектов.
- Широкое дерево с длинными именами.
- Поиск по дереву и фильтры расширений.
- Выделение файлов/папок и возврат из viewer к дереву.
- Копирование пути для файлов/папок.
- Иерархия папок, подпапок и файлов визуально различается; линии связей показывают вложенность.

### PDF

- Массовый обзор строится в 150 DPI.
- Активная большая страница строится в 300 DPI.
- Кэш разделён по качеству и повторное обращение к готовой странице не должно заново рендерить её.
- Миниатюра — отдельная страница многостраничного PDF.
- Viewer принят: масштаб, `Вписать`, поворот, рука/стрелка, перетаскивание, средний/полный/стандартный режимы.
- Растровые (сканированные) PDF тоже должны показываться. Наличие миниатюры при пустом большом поле требует проверки фактического `img.src`, HTTP cache PNG и слоя viewer, а не предположения, что «растровый PDF не поддерживается».

### DWG

- Если есть корректная PDF-пара, DWG получает PDF-превью.
- Если пары нет, файл DWG остаётся видимым и открываемым; viewer показывает явное состояние «PDF-пара не найдена», а не скрывает файл.
- Сопоставление DWG–PDF должно быть консервативным: нормализовать проектные шифры и разделители, сопоставлять сильные общие части названия, но не связывать сомнительные пары из разных разделов/частей.
- DWG открывается в нативной Windows-программе. Пользователь использует AutoCAD; проблемы первого запуска/только-чтение/пустое окно необходимо диагностировать реальными логами, а не менять viewer вслепую.
- Экспериментальный рендер модели DWG не является заменой нативному CAD и должен оставаться отдельным, явно обозначенным экспериментом.

### Вортекс (Word)

- Название универсального контура превью: `Вортекс` / `Vortex`.
- `.doc` и `.docx`: Word → PDF cache → принятый PDF-viewer.
- `.gdoc`: виден и открывается как shortcut, но локально через Word не рендерится; показывается понятная заглушка.
- Всегда доступна кнопка нативного открытия Word.

### Вортекс (Excel)

- Launcher — только read-only просмотр, не второй Excel.
- `.xlsx`/`.xlsm`: HTML-кэш на каждый лист книги.
- Большой Excel-view сохраняет вкладки листов, ширины столбцов, высоты строк, merges, базовые шрифты/заливки, прокрутку, масштаб и панорамирование.
- Миниатюра Excel — уменьшенное окно того же HTML-листа. Нельзя создавать второй «упрощённый» рендерер/картинку для карточки: это уже приводило к неверным базовым линиям текста, обрезанным строкам и расхождению с большим видом.
- Синхронно готовится первый выбранный лист, остальные — в фоне по одному.
- Название книги показывается полностью в интерфейсе; карточки не должны заменять имя многоточием.
- Вкладки листов — обычные HTML-кнопки с немедленным active state. Запрещены экспериментальные перекрывающиеся «браузерные» вкладки, SVG-фоны, псевдоэлементные капли и подобные эффекты: они дали артефакты и задержку нажатия.

## 5. Единые правила viewer

Нижняя панель одна для PDF, DWG preview, Word и Excel:

- `−`, `+`, `Вписать`;
- поворот;
- рука/стрелка;
- три режима просмотра;
- кнопка `Открыть ...` в нативной программе для исходного файла.

Не создавать урезанный вариант панели для Excel или Word. Русская надпись `Вписать` всегда должна целиком помещаться в кнопке. Рука — чёрный лёгкий контур кисти, не жёлтая заливка и не текстовая надпись.

Excel HTML — это overlay. Его `hidden` обязан реально означать `display: none`; иначе невидимый Excel iframe перекрывает PDF/DWG/Word и создаёт ложное впечатление пустого большого поля.

Любое изменение общей панели проверять в реальном браузере минимум на PDF/DWG и Excel, а не только на одном формате.

## 6. Кириллица и Windows-пути

- Все исходники, Markdown, JSON, HTML, CSS, JS, Python и манифесты — UTF-8.
- До и после изменения русского текста, путей или UI запускать:

```text
scripts\check_encoding.cmd
```

- Не делать вывод о кодировке по одному выводу PowerShell: консоль Windows может показать корректный UTF-8 как «кракозябры».
- Для проверки использовать браузер, UTF-8-aware чтение или Unicode-диагностику.
- Статические text-ответы backend обязаны отправляться с `charset=utf-8`.

## 7. Чего делать нельзя

1. Не использовать Google Drive `G:`, `H:` или `I:` как live runtime или источник запуска backend.
2. Не писать исходный код v3 в Google Drive как альтернативную рабочую копию.
3. Не создавать очередной `launcher_v2`, `Launcher_Runtime`, `F-Engineering_Launcher-H`, демо-клон или сервер на случайном порту.
4. Не удалять или изменять клиентские оригиналы в подключённых объектах: кэш всегда производный и отдельно удаляемый.
5. Не коммитить `runtime`, кэши, rendered previews, журналы, манифесты объектов, клиентские документы и секреты.
6. Не заменять нативные CAD/Office собственным редактором.
7. Не объявлять работу готовой без browser QA на реальных файлах.
8. Не менять сразу дизайн, backend и конвейер рендера в одной правке.
9. Не возвращать экспериментальные вкладки с перекрытием; использовать проверенные кнопки.
10. Не «исправлять» DWG–PDF пары простым совпадением коротких слов вроде «Общие данные» без проверки раздела, кода и значимых фрагментов.

## 8. Режим разработки и проверки

Для каждого небольшого изменения:

1. определить конкретную подтверждённую причину;
2. внести малую правку только в необходимый слой;
3. проверить файл/кодировку;
4. открыть Launcher из `scripts\start_windows.cmd`;
5. провести короткую реальную Browser QA;
6. описать результат и следующий шаг;
7. только затем делать следующую правку.

Если пользователь сообщает «не работает», сначала подключиться к его активной вкладке и собрать состояние DOM, console, network, viewer state и server log. Нельзя отвечать «исправлено», если фактическая проверка не показала результат.

## 9. Ближайшие задачи

1. Стабилизировать открытие файлов в нативных программах: PDF, DWG/AutoCAD, Word и Excel должны открываться быстро и повторяемо. Использовать чек-лист и логи.
2. Закончить аккуратный эксперимент с DWG без PDF-пары: полезная обзорная визуализация модели, но не обещание точного CAD-рендера.
3. Продолжить наблюдение за реальными объектами и багами, не расширяя одновременно весь дизайн.
4. После стабильности подготовить переносимую демонстрационную сборку для другого Windows-компьютера. Не пытаться размещать локальный Windows-runtime на VPS как замену desktop-версии.
5. Затем развивать ограниченные прикладные модули обработки. У каждого должны быть входные документы, понятная кнопка, результат, уровень уверенности и воспроизводимый журнал.
