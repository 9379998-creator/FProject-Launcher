## 3. Архитектура обработки Word (DOC / DOCX)

### 3.1. Двухстадийный конвейер (Word -> PDF -> PNG):
Лаунчер отображает все документы как графические листы на холсте с возможностью масштабирования, вращения и панорамирования. Для файлов Word (.doc, .docx):

```
Исходный Word (.doc/.docx)
    │
    ▼ (scripts/convert_word_to_pdf.ps1 через Word COM)
Векторный многостраничный PDF (runtime/cache/word/<hash>/<name>.pdf)
    │
    ▼ (PyMuPDF / Poppler в server.py)
Растровые страницы PNG (runtime/cache/pdf/<hash>/page-<N>.png)
    │
    ▼
Миниатюры в ленте (Ribbon) и просмотрщик на большой сцене (Stage)
```

1. **Стадия 1: Экспорт в PDF (`word_to_pdf` в `server.py`, строки 580–656)**
   - Проверяется кэш по mtime и размеру файла.
   - Если кэша нет, вызывается PowerShell скрипт `scripts/convert_word_to_pdf.ps1` через COM-объект `Word.Application` (`$word.Documents.Open`, `$document.SaveAs2($OutputPath, 17)`).
   - **Важно:** Microsoft Word сохраняет **абсолютно все страницы документа целиком** в промежуточный PDF-файл в `runtime/cache/word/`! То есть на этом этапе документ на 35 страниц уже содержит все 35 страниц.

2. **Стадия 2: Растеризация в PNG (`render_word` -> `render_pdf`, строки 659–667 и 1406–1535)**
   - Вызывается функция `render_pdf(pdf_path, dpi=dpi, first_page_only=first_page_only)`.
   - В `render_pdf` реализован цикл по страницам через PyMuPDF (`fitz`):
     ```python
     pages_to_render = 1 if first_page_only else page_count
     for page_idx in range(pages_to_render):
         page_num = page_idx + 1
         png = target_dir / f"page-{page_num}.png"
         ...
     ```
   - Если передан флаг `first_page_only = True`, PyMuPDF рендерит **только `page-1.png`**.
   - Ответ API содержит:
     `totalPages: 35, renderedPages: 1, items: [{ page: 1, url: ... }]`

## 4. Почему рендерится только первая страница: Глубинные первопричины (Root Causes)

### Первопричина №1: Жестко зашитый параметр `firstPageOnly: true` в батч-рендере (`app.js`)
В файле `app/frontend/app.js` функция `renderBatch` формирует запрос к серверу:
```javascript
// app.js, строки 2846-2850
const requestBody = {
  files: itemsToFetch.map((file) => file.path),
  dpi: PDF_PREVIEW_DPI,
  firstPageOnly: true, // <--- ЗДЕСЬ ПРИНУДИТЕЛЬНО 1 СТРАНИЦА
};
```
**Зачем это было сделано автором:**
Это была оптимизация каталога: если пользователь кликает по папке, в которой лежит 30 файлов по 50 страниц (всего 1500 страниц), рендеринг всех страниц за один раз заблокировал бы приложение на 5–10 минут. Поэтому для каждого файла в папке запрашивался только 1-й титульный лист в качестве миниатюры.

### Первопричина №2: Отсутствие подгрузки остальных страниц при просмотре из папки
В `renderBatch` догрузка остальных страниц (`streamRemainingDocumentPages`) была завязана строго на флаг одиночного файла:
```javascript
// app.js
if (isSingle && payload.documents?.[0]?.pages > 1) {
  streamRemainingDocumentPages(payload.documents[0], itemsToFetch[0]);
}
```
Когда пользователь выбирает папку `договор`:
- `isSingle === false` (потому что выбрана папка, а не одиночный файл).
- В результате `streamRemainingDocumentPages` **никогда не запускался**.
- В ленте оставался только лист №1.
- При клике по этому листу на сцену выводился лист №1, а страницы со 2 по 35 оставались невидимыми и незапрошенными.

### Первопричина №3: Несогласованность эндпоинтов `/api/word/page` vs `/api/pdf/page`
В бэкенде `server.py` есть два раздельных эндпоинта подгрузки отдельных страниц:
1. `POST /api/pdf/page` (строка 2058):
   - Ожидает `{ "file": "<путь к PDF>", "page": N }`.
   - Если передать путь к файлу `.doc` или `.docx`, бэкенд выбросит исключение: `ValueError("Это не PDF-файл")`.
2. `POST /api/word/page` (строка 2106):
   - Ожидает `{ "file": "<путь к DOCX>", "page": N }`.
   - Находит или генерирует промежуточный PDF и рендерит страницу N.

А функция `streamRemainingDocumentPages` в `app.js` жестко вызывала `/api/pdf/page`.
Если в `docPath` передавался оригинальный путь к `.docx`, сервер отвечал `400 Bad Request ("Это не PDF-файл")`, и поток страниц прерывался.

### Первопричина №4: Потеря `sourcePath` в структуре объектов страниц
Когда батч возвращал `payload.documents`, поле `document.path` содержало путь к кэшированному PDF в `runtime/cache/word/...`.
В создаваемых объектах страниц `documentPath` указывал на кэш, а `sourcePath` (путь к исходному `.docx`) не сохранялся. В результате:
- Синхронизация с деревом файлов (`revealPathInTree`) не могла найти файл в дереве.
- Копирование пути и системные действия ссылались на временные файлы кэша.

## 5. Что уже сделано в текущей версии

1. **Сохранение метаданных и исходных путей:**
   - В `render_pdf` (строки 1523 и 1608 `server.py`) теперь всегда возвращается `"sourcePath": str(path)`.
   - В `renderBatch` (строки 2880–2900 `app.js`) каждый объект страницы получает `sourcePath: realSourcePath`, `previewFor: { path: realSourcePath, name: realName }`, `totalPages: document.pages`.
2. **Умная вставка страниц в ленту (`insertAfterKey`):**
   - Функция `appendPagesToViewer(pages, insertAfterKey)` обновлена: теперь при догрузке страниц документа (2, 3, 4...) они вставляются **строго следом за предыдущей страницей этого же документа**, а не в конец всей ленты каталога.
3. **Автоподгрузка при клике / просмотре:**
   - В `showPdfPage` добавлен триггер: если документ имеет `totalPages > 1` и страницы еще не догружены, инициируется фоновая подгрузка оставшихся страниц через `streamRemainingDocumentPages`.
4. **Гарантированное открытие в проводнике:**
   - В `server.py` реализована отдельная функция `open_in_explorer(path: Path)`, использующая системный `subprocess.Popen(["explorer.exe", f"/select,{resolved}"])` без перехвата нативными программами.
   - В `app.js` вызовы «Открыть в проводнике» переведены на эндпоинт `/api/open-explorer`.
5. **Отказоустойчивый буфер обмена:**
   - Добавлен цикл ожидания для Win32 API и системный фоллбэк на `clip.exe` с UTF-16LE.

## 6. Задачи и рекомендации для следующего агента

Следующему агенту рекомендуется проанализировать и реализовать один из следующих подходов:

### Вариант А: Разделение логики «Клик по папке» vs «Клик по файлу в дереве» (Рекомендуется)
- **Если пользователь выбрал папку в дереве:**
  - В каталоге рендерится по 1-й странице каждого документа (`firstPageOnly: true`).
  - При клике на миниатюру документа в ленте — на сцене отображается титульный лист, а в ленту догружаются страницы 2..N именно этого документа.
- **Если пользователь кликнул конкретный файл Word (.doc / .docx) в дереве:**
  - Запрос к `/api/word/render` должен отправляться с `firstPageOnly: false`.
  - В этом случае Word-документ сразу отрендерит все свои 35 страниц в ленту без необходимости ожидания догрузки.

### Вариант Б: Режим «Книга / Пагинатор» на большой сцене
- При просмотре многостраничного Word/PDF на сцене добавить на панель управления сцены пагинатор:
  - Кнопки: `[ < Предыдущая ]` `Стр. X из Y` `[ Следующая > ]`.
  - Прямой переход к странице через вызов `/api/word/page` (для DOCX) или `/api/pdf/page` (для PDF) с сохранением уже отрендеренных страниц в кэше `highQualityPages`.
  - Это предотвратит раздувание горизонтальной ленты миниатюр до сотен страниц при просмотре больших договоров.

### Вариант В: Проверка совместимости формата .DOC (Word 97-2003)
- В папке пользователя `договор` есть как современные файлы `.docx`, так и старые `.doc` (бинарный формат Word 97-2003, например `Dogovor_Evromonolit_2_redak подпись.doc`).
- Убедиться, что PowerShell-скрипт `scripts/convert_word_to_pdf.ps1` корректно открывает старый бинарный формат без блокирующих диалоговых окон Word о защищённом просмотре.

## 8. Дополнительный инцидент для внимания: Сбой PyMuPDF на повреждённых деревьях структуры
При тестировании некоторых PDF-файлов (особенно экспортированных из САПР/Word) зафиксировано падение с сообщением в stderr:
`MuPDF error: format error: No common ancestor in structure tree`
В PyMuPDF (`fitz`) библиотека MuPDF на уровне C при нарушении структуры дерева тегов может завершать работу процесса.  
**Рекомендация:** В функции `render_pdf` обернуть вызов PyMuPDF или при обнаружении подобных ошибок перенаправлять рендеринг в Poppler (`pdftoppm`), который полностью игнорирует дефекты дерева структуры и успешно растеризует такие файлы.
