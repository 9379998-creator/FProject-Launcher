# Дорожная карта: объект как динамические данные

**Статус:** черновик к обсуждению.
**Дата:** 2026-08-15.

## 1. Что меняется в постановке

Сейчас объект (папка) обрабатывается как статичный снимок: один раз загрузили,
manifest.json описывает его «навсегда». Пользователь вынужден сам понимать, что
папка устарела.

Новая постановка: объект — живые данные. Файл, который уже был в объекте, может
измениться (пункт 1). Извне могут прийти новые файлы (пункт 2). Также могут
исчезнуть старые (пункт 3, обязательный для полноты). Вся динамика должна быть
видна в Launcher.

## 2. Факты текущей реализации (2026-08-15)

| Что | Где | Как |
|---|---|---|
| Кнопка «Обновить» | `app.js:1476-1479` | `importObject(true)` → повторный `scan_object`, полный сброс UI |
| Полный обход папки | `server.py:117` `scan_object` | переписывает manifest целиком |
| Сброс состояния UI | `app.js:768-786` | выделение, фильтр, свёрнутые папки, превью |
| Метаданные файла в manifest | `server.py:102-110` | только `name`, `path`, `extension`, `size` — **без mtime** |
| Проверка свежести превью | `server.py:180-189, 338-347` | cacheKey = mtime_ns + size, есть у PDF/Word/Excel/DWG |

Вывод: рендер-слой уже умеет отличать «файл не менялся» от «файл менялся»,
но только в момент перерисовки листа. Слой данных (manifest) не хранит
идентичность файла, поэтому diff невозможен, а UI при обновлении теряет контекст.

## 3. Ключевые решения до этапов

1. **Идентификатор файла — относительный путь.** Внутри объекта файл
   однозначно определяется относительным путём от корня объекта.
2. **Сигнатура содержимого — mtime_ns + size.** Достаточна для обычного случая
   и дешёвая. Строгая проверка (хэш) — отдельный режим для критичных файлов,
   не для всей папки.
3. **Previous snapshot.** Хранить предыдущий скан рядом с текущим, чтобы diff
   был явным и повторяемым, а не «сохранить в памяти процесса».
4. **Diff не должен сбрасывать UI.** Обновление дерева — инкрементальное,
   с сохранением выделения, прокрутки, фильтров и открытых превью.
5. **Правило кэша не меняется:** кэш никогда не подменяет исходник; удалённый
   файл не исчезает из дерева молча — он становится «удалён» до подтверждения.

## 4. Этапы

### Этап 1 — идентичность файла в manifest

- Добавить в файловые узлы дерева поля `mtimeNs` и `size` (size уже есть).
- При изменении/добавлении/удалении хранить рядом с manifest.json предыдущий
  снимок (или файл-уровневую таблицу сигнатур).
- Наполнить manifest полем `sourceIdentity` (путь + mtimeNs + size) для каждого
  файла — то, что уже используется рендер-слоем, поднять на уровень данных.

Выход: manifest способен ответить «этот файл изменился с прошлого скана».

### Этап 2 — backend: инкрементальный скан и diff

- Новый endpoint `/api/objects/diff`: обход без ре-сканирования тяжёлых
  операций — только `stat` по известному списку путей + обнаружение новых.
- Возвращать множества:
  - `added` — новые относительные пути;
  - `changed` — тот же путь, другая mtime/size (или хэш в строгом режиме);
  - `removed` — пути, которых больше нет;
  - `unchanged` — остальное.
- Сохранять результат как `object.diff.json` рядом со снимком.

Выход: у пользователя есть машиночитаемый ответ «что именно изменилось».

### Этап 3 — frontend: показать динамику, не сбрасывать контекст

- Панель-сводка: «Добавлено: N · Изменено: M · Удалено: K».
- Бейджи на узлах дерева: NEW (зелёный), CHANGED (жёлтый), REMOVED (красный,
  зачёркнут), с агрегацией на папки (в папке 3 изменённых файла).
- Фильтр «только изменённые/новые» для быстрого триажа.
- Патч дерева на месте: выделение, прокрутка, свёрнутые папки и открытые превью
  сохраняются.
- Строки статуса свежести: «актуально / изменено / требует обновления».

Выход: динамика видна, контекст не теряется.

### Этап 4 — инвалидация превью по diff

- Для `changed` и `added`: пометить превью как устаревшее, показать спиннер и
  перерисовать по требованию или в фоне.
- Для `unchanged`: не трогать кэш (уже работает через cacheKey).
- Для `removed`: превью остаётся доступным, но с явной пометкой «файл удалён
  из исходника».

Выход: превью всегда соответствует исходнику, без полной перерисовки.

### Этап 5 — автообнаружение изменений

- Лёгкий фоновый опрос (`stat`-только) с дебаунсом, либо подписка
  ReadDirectoryChangesW (watchdog) для папок без сетевых ограничений.
- Объединение всплесков событий: сохранение из Office — это temp+rename,
  один «файл изменился», а не «удалился+создался».
- Пометка файлов «записывается» (size=0, блокировка) с повторной попыткой.

Выход: пользователь не обязан жать «Обновить» — объект сам сообщает о динамике.

### Этап 6 — устойчивость к краевым случаям

- Переименование: temp+rename при сохранении Word/Excel не должен показываться
  как «удалён+добавлен»; распознавать по размеру/содержимому или атомарному
  rename-событию.
- Ошибки доступа, сетевые диски, файлы «пишутся прямо сейчас» — не роняют скан;
  помечаются «недоступен» и повторяются.
- Контрольная точка A (критерий успеха): пользователь оставил объект открытым,
  файл изменился извне, вернулся — видит бейдж CHANGED, актуальное превью и
  сохранившийся контекст, без полного перестроения.

## 5. Критерий успеха этапа (контрольная точка)

1. Изменился существующий файл → бейдж CHANGED + перерисованное превью.
2. Пришёл новый файл → бейдж NEW + сводка «Добавлено: 1».
3. Удалён файл → пометка REMOVED, а не исчезновение из дерева.
4. UI не сбрасывается: выделение, фильтр, прокрутка и открытые превью на месте.
5. Повторное открытие уже подготовленного объекта — практически мгновенно
   (без тяжёлых операций по `unchanged`).
