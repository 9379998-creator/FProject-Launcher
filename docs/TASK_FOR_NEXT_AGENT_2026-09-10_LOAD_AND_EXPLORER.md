# Задача для ИИ-агента: Устранение сбоев «Загрузить» и «Открыть в Проводнике»

> **Дата документа:** 10 сентября 2026 г.  
> **Статус проекта:** В разработке (ветка `main`, базовый коммит `402d96f`).  
> **Окружение:** Windows 10/11, Python 3.14, Microsoft Edge WebView2 (`pywebview`), виртуальные диски Google Drive (`H:\`).

---

## 1. Контекст и что уже сделано (начиная с коммитов `06747b4`..`402d96f`)

В последних коммитах и текущей сессии были реализованы следующие улучшения, которые **успешно приняты пользователем**:

1. **Дизайн дерева папок и файлов под стиль Проводника Windows:**
   - Папки и файлы теперь сидят плотно и компактно (уменьшены вертикальные отступы `min-height: 20px`, плотная посадка строк).
   - Заменены иконки на строгие монохромные SVG в нативном стиле Windows Explorer.
   - Убраны громоздкие лишние элементы оформления.

2. **Раскрытие и сворачивание папок по клику на саму строку:**
   - Раскрытие/сворачивание теперь происходит при клике на саму папку (на иконку или текст строки), а не только по микроскопической стрелочке слева.
   - **Скорость:** Устранены 1.5–2 секундные задержки. Теперь сворачивание/разворачивание происходит мгновенно (in-place переключение CSS-класса `collapsed` на дочернем контейнере `.tree-children`, без перерисовки всего DOM-дерева).

3. **Сквозная 3-сторонняя синхронизация (Tree ↔ Thumbnails ↔ Stage Viewer):**
   - Клик по файлу в левом дереве мгновенно выбирает миниатюру в ленте внизу и открывает просмотр на центральном экране (Stage).
   - Клик по миниатюре в ленте прокручивает левое дерево к выбранному файлу с подсветкой (`thumb-reveal`).
   - Навигация с клавиатуры: стрелки `Вверх` / `Вниз` перемещают фокус по дереву и сразу обновляют просмотр; `Влево` / `Вправо` перелистывают многостраничные документы.

4. **Копирование пути:**
   - Кнопка копирования пути (значок `⧉`) в дереве и на панели управления теперь работает корректно и копирует валидный путь в буфер обмена Windows.

## 3. Что было предпринято предыдущим агентом и ПОЧЕМУ ЭТО НЕ СРАБОТАЛО

Предыдущий агент провел ряд правок, которые успешно проходили локальные тесты из консоли, **но всё равно не работают для пользователя в GUI**:

### А. Попытки исправить кнопку «Загрузить»
1. **Что было сделано:**
   - В `scripts/choose_folder.ps1` был обнаружен ошибочный GUID `DC1C5A9C-E88A-4DDE-A5A6-60E4DB1AE11E`. Он был заменен на `DC1C5A9C-E88A-4DDE-A5A1-60F82A20AEF7` (реальный CLSID `CLSID_FileOpenDialog` в Windows).
   - Был добавлен `GetForegroundWindow()` в качестве родителя диалога.
   - В `app/backend/server.py` в эндпоинте `/api/choose-folder` были убраны флаги `hidden_process_kwargs()` (`SW_HIDE`, `CREATE_NO_WINDOW`), предполагая, что они скрывали окно диалога.
   - В `app/frontend/app.js` в `updateObjectButtons()` строка `els.load.disabled = tree;` была заменена на `els.load.disabled = false;`.
2. **Почему у пользователя это НЕ сработало (ФАКТИЧЕСКИЙ ЛОГ ИНЦИДЕНТА 05:27):**
   Реальный лог боевого сервера зафиксировал:
   ```text
   Exception occurred during processing of request from ('127.0.0.1', 57738)
   Traceback (most recent call last):
     File "server.py", line 1881, in do_POST
       proc = subprocess.run([sys.executable, str(choose_script)], timeout=120, ...)
   subprocess.TimeoutExpired: Command '['choose_folder.py']' timed out after 120 seconds
   ConnectionResetError: [WinError 10054] Удаленный хост принудительно разорвал существующее подключение
   ```
   **Вывод:** Пользователь нажал кнопку «Загрузить», запрос ушёл на сервер. `choose_folder.py` запустился и висел ровно 120 секунд, ожидая закрытия диалога. **Но пользователь диалог на экране не увидел!** Окно диалога открылось либо вне экрана/в скрытой сессии, либо под окном WebView2 без фокуса. Через 120 секунд вебвью разорвал соединение, и сервер аварийно завершился.

### Б. Попытки исправить «Открыть в Проводнике»
1. **Что было сделано:**
   - В `app/backend/server.py` функция `launch_native_file` была модифицирована:
     - Для папок: `subprocess.Popen(f'explorer.exe "{resolved}"')`.
     - Для файлов: `subprocess.Popen(f'explorer.exe /select,"{resolved}"')`.
     - Добавлен вызов Win32 API `ctypes.windll.user32.AllowSetForegroundWindow(0xFFFFFFFF)`.
     - Добавлены фоллбеки на `os.startfile(target_dir)` и `cmd.exe /c start`.
   - В `server.py` добавлены оба маршрута: `/api/open-file` и `/api/open-explorer`.
2. **Почему у пользователя это НЕ сработало:**
   - Пути пользователя находятся на Google Диске (`H:\Общие диски\...`). На этой файловой системе Windows Explorer ведет себя нестандартно при запуске из фонового веб-сервера.
   - Кроме того, в системе работало несколько процессов `python.exe` / `pythonw.exe`: старый орфанный сервер висел на порту 8780, а новый поднимался на 8781. Окно `flauncher.pyw` подключалось к первому живому порту (8780) и общалось со **старым сервером**, в котором новые фиксы вообще отсутствовали!
   - В самом WebView2 клики по ссылкам/кнопкам могут перехватываться внутренними обработчиками событий, либо fetch запрос отменяется при перерисовке или потере фокуса.

## 4. Что КАТЕГОРИЧЕСКИ НЕЛЬЗЯ ДЕЛАТЬ следующему агенту

1. **Не делать свой браузерный диалог файлов:**  
   Пользователь категорически против самодельных JS-окон с выбором путей. Никаких «встроенных проводников» в HTML/JS. Только нативный системный механизм Windows.
2. **Не полагаться на `os.startfile` вслепую:**  
   `os.startfile(folder)` на сетевых/виртуальных дисках Google Диска `H:\` часто завершается с кодом 0, но фактически окно Explorer не создаёт (`MainWindowHandle == 0`).
3. **Не коммитить код в git до реальной проверки:**  
   Пользователь потребовал: *«Не коммить, пока собственными ручками не проверишь»*.
4. **Не плодить зомби-процессы серверов на разных портах:**  
   `flauncher.pyw` перебирает порты 8780..8789. Если на 8780 висит старый процесс, пользователь видит старую версию, сколько бы правок ни вносилось в код.

## 5. Рекомендуемые пути решения для следующего интеллекта

Следующий агент должен подойти к решению фундаментально, а не косметически:

### Путь 1: Использовать нативный мост `pywebview.api` (Рекомендуется!)
Сейчас приложение открывается через `pywebview` в `app/flauncher.pyw`.  
Вместо того чтобы из JavaScript слать `fetch` на HTTP-сервер, который через `subprocess` пытается вызвать PowerShell:
1. В `app/flauncher.pyw` объявить класс API окна:
   ```python
   class LauncherWindowApi:
       def choose_folder(self):
           import webview
           # pywebview имеет встроенный нативный метод выбора папки,
           # привязанный напрямую к дескриптору окна:
           # window.create_file_dialog(webview.FOLDER_DIALOG)
       def open_in_explorer(self, path):
           # Прямой вызов Explorer из процесса окна приложения
   ```
2. Передать этот API в `webview.create_window(..., js_api=LauncherWindowApi())`.
3. В `app/frontend/app.js`:
   Если `window.pywebview?.api` доступен:
   - Вызывать `await window.pywebview.api.choose_folder()` — это на 100% откроет системный диалог выбора папки поверх окна лаунчера без сетевых задержек и проблем с правами процессов.
   - Вызывать `await window.pywebview.api.open_in_explorer(path)` — это гарантированно откроет Проводник.
4. Предусмотреть HTTP-фоллбек только для открытия в обычном браузере (Edge/Chrome).

### Путь 2: Исправление системного вызова через Win32 Shell API
Если использовать серверный подход:
1. Вызывать `ShellExecuteExW` через `ctypes` с флагом `SEE_MASK_NOASYNC`, передавая реальный дескриптор рабочего стола `GetDesktopWindow()`.
2. Для выбора папки использовать `IFileOpenDialog` не через PowerShell, а через нативный C-код или `ctypes` с правильной инициализацией COM-потока `CoInitializeEx(None, COINIT_APARTMENTTHREADED)`.

### Путь 3: Жёсткий контроль единого процесса сервера
1. В `app/flauncher.pyw` при старте принудительно завершать любые старые серверы лаунчера на портах 8780–8789, чтобы окно лаунчера ВСЕГДА подключалось к актуальному коду.
2. Проверять порт, на котором крутится текущий бэкенд, и убеждаться, что WebView2 делает запросы именно к нему.
